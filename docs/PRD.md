# 1. 产品概述

## 1.1 产品背景

人们经常会有一些想要购买的商品或想要实现的愿望。

这些愿望可能价格较高，也可能并非生活必需品，因此人们往往会给自己设定一些条件：

- 坚持健身 30 次，就奖励自己一台 Kindle。
- 连续 30 天不吃零食，就买一双喜欢的鞋。
- 通过兼职赚到 2000 元，就购买一款心仪的电子产品。
- 完成一个开源项目，就奖励自己一次旅行。
- 坚持阅读 100 小时，就购买一台新的平板电脑。

这些行为本质上是个人主动建立的一套奖励机制。

但目前缺少一个专门的工具帮助用户：

1. 记录自己想要的东西。
2. 为每个心愿设定个性化的达成条件。
3. 持续记录自己付出的努力。
4. 了解每个条件的完成进度。
5. 在达成目标时获得奖励解锁的成就感。

WishEarn 希望解决这个问题。

## 1.2 产品定位

WishEarn 是一个帮助用户将个人愿望转化为行动目标，并通过持续努力获得奖励的个人激励应用。

核心理念：

**让每一份想要，都有值得付出的努力。**

产品核心循环：

心愿创建 → 条件设定 → 持续行动 → 进度追踪 → 心愿解锁 → 奖励兑现。

## 1.3 产品目标

### 用户目标

- 记录自己真正想要的东西。
- 为想要的东西设置具有个人意义的目标。
- 让抽象的自律行为变得有明确的方向。
- 通过可视化进度获得持续的正反馈。
- 通过完成目标获得奖励和成就感。

### 产品目标

MVP 阶段重点验证：

1. 用户是否愿意为心愿设置条件。
2. 用户是否愿意持续记录条件完成情况。
3. 心愿与行动绑定是否能够提高用户的持续使用意愿。
4. 用户是否能够从心愿解锁中获得明显的满足感。

不以用户打卡次数作为唯一成功指标。

# 2. 产品理念与设计原则

## 2.1 核心理念：A 为主，B 为辅

### A：努力换奖励（核心模式）

用户通过完成自己设定的行为目标，获得心愿的购买或实现资格。

例如：

心愿：Kindle Paperwhite。

解锁条件：
- 健身 20 次。
- 阅读 30 天。
- 连续 30 天不吃零食。

所有条件完成后，心愿解锁。

这里的关键不是商品价格，而是用户为获得奖励付出的努力。

### B：努力积累资金（辅助模式）

用户通过额外收入、节约开支等方式，为心愿积累专项资金。

例如：

心愿：MacBook Pro。

目标金额：15000 元。

条件：
- 兼职收入累计 5000 元。
- 节约开支累计 3000 元。
- 完成一个额外项目。

第一版支持将金额积累作为一种普通条件类型，不建设独立的财务管理系统。

## 2.2 核心设计原则

**原则一：用户定义规则。**

不限制用户的目标类型和目标内容。系统提供模板，但不强制用户采用模板。

**原则二：心愿优先于任务。**

所有行动都应该服务于某个心愿。避免产品退化为普通 Todo 或 Habit Tracker。

**原则三：记录努力，而非制造压力。**

不通过连续打卡失败、排行榜、惩罚等机制给用户制造焦虑。

**原则四：每一步努力都应该可见。**

用户能够知道自己已经做了什么，以及距离获得奖励还有多远。

**原则五：奖励解锁应该具有仪式感。**

完成心愿应该成为一个值得庆祝的时刻。

# 3. 用户画像与使用场景

## 3.1 目标用户

主要面向：

- 有明确消费愿望的年轻用户。
- 希望提升自律能力的人群。
- 喜欢健身、阅读、学习和个人成长的人群。
- 希望通过目标管理减少冲动消费的人群。
- 喜欢通过完成挑战获得成就感的人群。

## 3.2 典型场景

### 场景一：健身换奖励

用户想购买一双价格 1200 元的跑鞋。

创建心愿：
- 名称：Nike 跑鞋。
- 条件：累计跑步 100 公里。
- 条件：累计健身 20 次。

之后每天记录运动情况。

所有条件达成后，跑鞋心愿解锁。

### 场景二：戒除不良习惯

用户想买一台 Kindle。

创建心愿：
- 条件：连续 30 天不吃零食。
- 条件：累计阅读 30 小时。

用户每天记录自己的情况。

### 场景三：兼职赚钱

用户想买一台 MacBook。

创建心愿：
- 条件：兼职收入累计 5000 元。
- 条件：完成一个技术项目。

其中收入条件通过手动填写金额进行累计。

### 场景四：多个心愿并行

用户同时拥有：
- Kindle：阅读目标。
- 跑鞋：运动目标。
- iPad：兼职收入目标。

每个心愿拥有独立的条件、进度和生命周期。

# 4. 核心业务模型

整个产品由三个核心业务对象构成。

## 4.1 Wish：心愿

代表用户想要获得的奖励。

属性：
- 心愿名称。
- 心愿图片。
- 参考价格。
- 描述。
- 创建时间。
- 目标日期（可选）。
- 当前状态。
- 关联条件。
- 总体进度。

心愿状态：

| 状态 | 含义 |
|---|---|
| ACTIVE | 进行中 |
| UNLOCKED | 已解锁 |
| COMPLETED | 已兑现 |
| PAUSED | 已暂停 |
| ARCHIVED | 已归档 |

状态说明：

- ACTIVE：用户正在为心愿努力。
- UNLOCKED：所有必要条件已完成，可以领取奖励。
- COMPLETED：用户已经实际购买或实现心愿。
- PAUSED：用户暂时停止该心愿。
- ARCHIVED：用户主动归档，不再追踪。

## 4.2 Condition：条件

代表用户为心愿设定的达成要求。

一个心愿可以拥有一个或多个条件。

第一版支持以下六种类型：

| 类型 | 枚举 | 说明 |
|---|---|---|
| 连续坚持 | STREAK | 连续 N 天完成某行为 |
| 累计次数 | COUNT | 累计完成 N 次 |
| 累计时长 | DURATION | 累计达到 N 小时或分钟 |
| 累计金额 | AMOUNT | 累计获得或节省 N 元 |
| 目标完成 | CHECKPOINT | 完成某个具体事项 |
| 自定义 | CUSTOM | 自由定义条件及完成方式 |

每个条件支持：

- 条件名称。
- 条件描述。
- 条件类型。
- 目标值。
- 当前值。
- 单位。
- 是否必需。
- 权重。
- 创建时间。
- 完成状态。

第一版建议所有条件默认为必需条件，暂不开放复杂的 AND/OR 组合。

## 4.3 Progress：进度记录

代表用户实际完成的一次行动。

例如：

心愿：Kindle。

条件：健身 20 次。

进度记录：

| 日期 | 行动 | 数值 |
|---|---|---|
| 11-01 | 跑步 | 1 次 |
| 11-03 | 健身 | 1 次 |
| 11-05 | 游泳 | 1 次 |

每条记录支持：
- 关联条件。
- 记录时间。
- 数值。
- 单位。
- 备注。
- 创建时间。

必须保留历史记录，不允许通过直接修改当前累计值的方式替代历史数据。

# 5. 功能需求

优先级说明：

- P0：MVP 必须实现。
- P1：重要，但允许后续迭代。
- P2：暂不开发。

## 5.1 心愿管理

### FR-001 创建心愿（P0）

用户可以创建新的心愿。

字段：
- 名称：必填。
- 图片：选填。
- 描述：选填。
- 参考价格：选填。
- 目标日期：选填。

验收标准：
- 名称不能为空。
- 支持从系统相册选择图片。
- 不填写价格也可以创建。
- 创建成功后进入心愿详情或条件配置流程。

### FR-002 编辑心愿（P0）

允许修改名称、图片、描述、价格和目标日期。

修改心愿基础信息不应该影响已有进度记录。

### FR-003 删除心愿（P0）

用户可以删除心愿。

需要二次确认。

删除时应处理关联条件和历史记录，确保数据一致性。建议采用事务处理，并在 UI 明确说明删除后不可恢复。

### FR-004 心愿列表（P0）

首页展示用户所有心愿。

支持分类：
- 全部。
- 进行中。
- 已解锁。
- 已兑现。
- 已暂停。

每张心愿卡片展示：
- 图片。
- 名称。
- 当前进度。
- 条件完成数量。
- 状态。

### FR-005 暂停与恢复（P0）

用户可以暂停心愿。

暂停期间不主动要求用户打卡。

恢复后继续保留原有记录和进度。

暂停不自动视为失败。

### FR-006 归档心愿（P1）

允许将不再关注的心愿归档。

归档不删除历史数据。

## 5.2 条件管理

### FR-007 添加条件（P0）

创建心愿后，用户可以添加多个条件。

支持六种条件类型。

每种类型对应不同配置字段。

例如：

COUNT：
- 条件名称：健身。
- 目标值：20。
- 单位：次。

STREAK：
- 条件名称：不吃零食。
- 目标值：30。
- 单位：天。

DURATION：
- 条件名称：阅读。
- 目标值：100。
- 单位：小时。

AMOUNT：
- 条件名称：兼职收入。
- 目标值：1000。
- 单位：元。

CHECKPOINT：
- 条件名称：完成开源项目。
- 目标值：完成/未完成。

CUSTOM：
- 条件名称：自定义目标。
- 用户自行填写说明。

### FR-008 修改条件（P0）

允许修改条件名称、描述和目标值。

需要特别处理目标值小于当前累计值的情况。

建议：
- 允许修改。
- 修改后重新计算进度。
- 如果目标已经达到，则不能自动撤销已经解锁的心愿，需提示用户确认处理方式。

### FR-009 删除条件（P0）

删除条件时需要二次确认。

如果心愿已解锁，不允许删除条件导致历史解锁记录失去依据。

### FR-010 条件组合（P1）

预留以下组合方式：

- ALL：全部条件满足。
- ANY：任意条件满足。

MVP 只实现 ALL。

## 5.3 行动记录

### FR-011 手动打卡（P0）

用户可以为条件创建进度记录。

根据条件类型提供不同输入界面。

COUNT：
输入本次完成次数。

DURATION：
输入本次时长。

AMOUNT：
输入本次收入或节省金额。

STREAK：
记录当天是否完成。

CHECKPOINT：
标记目标是否完成。

CUSTOM：
允许用户填写数值或备注。

### FR-012 记录历史（P0）

用户可以查看某个条件的所有历史记录。

按时间倒序排列。

### FR-013 修改历史记录（P0）

允许修改历史记录。

修改后必须重新计算累计进度和心愿解锁状态。

### FR-014 删除历史记录（P0）

允许删除错误记录。

删除后重新计算条件进度。

### FR-015 今日行动汇总（P0）

提供今日行动入口，汇总用户所有进行中的条件。

支持快速打卡。

如果一个条件当天已经完成，可以展示已完成状态。

## 5.4 进度追踪

### FR-016 条件进度（P0）

显示：
- 当前完成值。
- 目标值。
- 剩余值。
- 完成百分比。

例如：

16 / 20 次，完成度 80%。

### FR-017 心愿总体进度（P0）

当所有条件都是必需条件时，采用条件完成度的平均值：

总体进度 = 已完成条件数量 / 条件总数量。

例如：

3 个条件：
- 健身：100%。
- 阅读：50%。
- 兼职：0%。

总体进度 = 50%。

注意：总体进度是展示指标，不能作为实际解锁判断依据。

### FR-018 进度历史（P1）

支持日历视图和趋势图。

## 5.5 心愿解锁

### FR-019 自动解锁（P0）

当所有必需条件满足时，自动将心愿状态变更为 UNLOCKED。

解锁必须通过统一的业务逻辑完成，不能仅依赖前端判断。

### FR-020 解锁仪式（P0）

展示专属解锁页面。

包括：
- 心愿图片。
- 心愿名称。
- 解锁成功提示。
- 完成时间。
- 完成的条件总结。

建议提供轻量动画和庆祝效果。

### FR-021 兑现奖励（P0）

用户点击「我已领取奖励」后，心愿状态变更为 COMPLETED。

记录兑现时间。

### FR-022 重新开启（P1）

已兑现的心愿可以复制为一个新心愿，但不直接修改原始完成记录。

## 5.6 资金积累

### FR-023 金额条件（P0）

支持通过 AMOUNT 条件累计资金。

例如：

兼职收入：
目标 1000 元，当前 600 元。

### FR-024 金额方向（P0）

金额条件应支持方向：

- INCOME：额外收入。
- SAVING：节省开支。
- OTHER：其他金额积累。

### FR-025 金额记录（P0）

用户手动输入金额，并填写备注。

MVP 不接入银行卡、支付平台或第三方财务账户。

金额记录只是心愿条件的进度，不构成真实资金托管或资产管理。

# 7. 核心业务规则

本章节是开发时必须遵守的规则。

## 7.1 心愿解锁规则

设一个心愿包含 N 个必需条件。

只有当所有必需条件都完成时，心愿才能解锁。

公式：

Unlock = Condition1 && Condition2 && ... && ConditionN

进度达到 100% 不应直接作为唯一解锁依据，必须检查每项条件的真实完成状态。

## 7.2 COUNT 规则

当前累计值：

CurrentValue = SUM(所有有效记录的数值)

完成条件：

CurrentValue >= TargetValue

例如：

目标 20 次。

记录 5 + 3 + 4 + 8 = 20。

条件完成。

## 7.3 DURATION 规则

当前累计时长：

CurrentValue = SUM(所有有效记录的时长)

完成条件：

CurrentValue >= TargetValue。

注意统一单位，建议内部使用秒或分钟，界面根据用户配置展示。

## 7.4 AMOUNT 规则

当前金额：

CurrentAmount = SUM(所有有效金额记录)

完成条件：

CurrentAmount >= TargetAmount。

金额使用 Decimal 或最小货币单位整数存储，禁止使用浮点数进行财务数值累计。

## 7.5 STREAK 规则

连续坚持型条件需要明确以下语义：

- 每个自然日最多完成一次。
- 按用户本地时区计算日期。
- 连续天数从第一次有效打卡开始计算。
- 中断后重新开始当前连续周期。
- 暂停期间不计算连续天数。
- 用户可以查看历史连续记录。

建议第一版不支持自动宽限日。

## 7.6 CHECKPOINT 规则

完成状态为 Boolean。

用户标记完成后，条件达成。

## 7.7 进度修改规则

所有进度都应从有效历史记录重新计算。

不要同时维护一个可以随意修改的累计值和一份独立的记录数据。

如果为了性能引入缓存或汇总字段，必须能够从历史记录恢复。

## 7.8 状态流转

ACTIVE → UNLOCKED → COMPLETED。

ACTIVE → PAUSED → ACTIVE。

ACTIVE → ARCHIVED。

PAUSED → ARCHIVED。

已完成心愿不可直接回到 ACTIVE。

- Wish(user_id, status)
- Condition(wish_id)

## 8.6 数据一致性

- 删除心愿时，在事务中处理关联条件及记录。
- 删除条件时，事务处理关联记录。
- 更新记录时，重新计算条件状态。
- 更新条件目标值时，重新计算完成状态。
- 心愿解锁必须具有原子性。
- 解锁事件不能因为重复触发而生成多次。

# 9. 交互与视觉设计规范

## 9.1 整体风格

关键词：

- 简洁。
- 温暖。
- 轻量。
- 有陪伴感。
- 有成就感。
- 不制造焦虑。

避免：
- 过度游戏化。
- 大量复杂图表。
- 强烈的竞争氛围。
- 过度商业化的商城风格。

## 9.2 视觉方向

建议采用现代 iOS 原生设计语言。

- 支持 Light / Dark Mode。
- 使用系统字体。
- 圆角卡片。
- 适当留白。
- 清晰的进度条。
- 柔和的状态色彩。

## 9.3 关键交互

创建心愿应该尽量简单。

建议流程：

第一步：添加心愿名称、图片和价格。

第二步：添加一个或多个解锁条件。

第三步：确认并创建。

不要在首次创建时要求用户填写大量不必要的信息。

## 9.4 解锁体验

解锁是产品最重要的情绪体验之一。

建议：

1. 触发轻量庆祝动画。
2. 展示心愿图片。
3. 展示「你做到了」。
4. 总结用户完成的所有条件。
5. 提供「领取我的奖励」按钮。

不要使用过度夸张的游戏化设计。

# 10. 技术架构建议

## 10.1 技术选型

MVP 建议优先使用原生 iOS 技术栈。

| 层级 | 技术 |
|---|---|
| 开发语言 | Swift |
| UI 框架 | SwiftUI |
| 最低系统版本 | iOS 17 |
| 本地持久化 | SwiftData |
| 图片选择 | PhotosPicker |
| 图片处理 | SwiftUI / UIKit |
| 图表 | Swift Charts |
| 本地通知 | UserNotifications |
| 测试 | XCTest / Swift Testing |

第一版不引入服务端。

## 10.2 架构模式

建议采用：

**SwiftUI + MVVM + Repository + Service**

建议目录：

WishEarn/
- App/
  - WishEarnApp.swift
  - AppRouter.swift
- Models/
  - User.swift
  - Wish.swift
  - Condition.swift
  - ProgressRecord.swift
- Views/
  - WishList/
  - WishDetail/
  - Today/
  - Achievements/
  - Settings/
  - Components/
- ViewModels/
- Repositories/
- Services/
  - ProgressService.swift
  - UnlockService.swift
  - StreakService.swift
  - ImageStorageService.swift
- Utilities/
- Resources/
- Tests/

## 10.3 架构要求

1. View 不直接操作数据库。
2. ViewModel 负责页面状态。
3. Repository 负责数据访问。
4. Service 负责业务规则。
5. UnlockService 是心愿解锁的统一入口。
6. ProgressService 是进度计算的统一入口。
7. 所有状态变化都应有明确的业务方法。

不要将业务逻辑散落在 SwiftUI View 中。

## 10.4 本地优先

第一版采用 Local-first 设计：

- 数据存储在本地。
- 无网络也能正常使用。
- 不要求用户注册。
- 图片保存在应用沙盒。
- 重要数据支持导出。

后续如果需要多设备同步，再引入 iCloud 或自建服务端。

## 10.5 数据迁移

必须考虑 SwiftData Schema Version。

数据库结构升级时，不能无故丢失用户心愿和历史记录。

## 11.1 性能

- 不强制注册。
- 不上传个人目标和行动记录。
- 不收集不必要的个人信息。
- 如未来引入云同步，明确告知数据使用方式。

## 11.4 可维护性

- 业务逻辑必须有单元测试。
- 数据模型和业务规则分离。
- 枚举值集中定义。
- 关键计算方法必须有测试覆盖。
- 不允许使用大量硬编码字符串。

# 13. 测试与验收标准

以下是 MVP 必须通过的业务测试。

## 13.1 心愿创建

- 创建不带图片的心愿。
- 创建带图片的心愿。
- 创建不填写价格的心愿。
- 创建没有条件的心愿时，不能直接解锁。
- 删除心愿后，关联数据得到正确处理。

## 13.2 条件计算

COUNT：
- 多条记录累计正确。
- 修改记录后重新计算。
- 删除记录后重新计算。
- 超过目标值时仍显示合理进度，不出现负数。

DURATION：
- 小时和分钟换算正确。
- 累计时长准确。

AMOUNT：
- 金额计算精确。
- 支持小数金额。
- 不同方向的记录正确累计。

STREAK：
- 连续两天正确计算。
- 中断一天后正确重置当前连续周期。
- 同一天重复打卡不能增加连续天数。
- 跨越午夜及用户时区变化时计算正确。
- 暂停期间不增加连续天数。

CHECKPOINT：
- 未完成时进度为 0。
- 完成后进度为 100%。

CUSTOM：
- 用户填写的信息可以正确保存和展示。

## 13.3 解锁逻辑

测试以下情况：

1. 一个条件完成，心愿解锁。
2. 多个条件全部完成，心愿解锁。
3. 多个条件只完成部分，不解锁。
4. 修改历史记录导致条件未完成，正确处理解锁状态。
5. 删除记录导致条件未完成，正确处理解锁状态。
6. 重复触发解锁逻辑，不重复创建解锁事件。
7. 已兑现心愿不会因为重新计算而丢失兑现记录。

特别要求：

对于已经解锁或兑现的心愿，后续用户修改历史记录时，应保留历史解锁事件，并提示用户当前条件是否仍然满足。

不能简单地静默撤销已发生的奖励解锁。

## 13.4 持久化

- 应用关闭后重新打开，数据完整。
- 图片路径有效。
- 多个心愿的数据互不影响。
- 数据库迁移后数据完整。

# 16. MVP 最终验收定义

WishEarn 第一版只有在以下完整流程能够真实运行时，才算完成：

**用户创建心愿 → 添加多个自定义条件 → 每天记录行动 → 系统计算进度 → 全部条件达成 → 自动解锁 → 用户领取奖励 → 历史心愿进入成就页面。**

- 所有数据能够持久化。

- 具备完整异常处理。

这条完整链路是 MVP 的第一优先级。
